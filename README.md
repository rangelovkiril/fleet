# fleet

`fleet` is the Flux GitOps repository for the k3s cluster that runs the RampMe backend, a live public transport map for Sofia whose core feature is wheelchair ramp reservation: a rider near a stop requests a ramp, and hardware on the vehicle deploys it over MQTT when the vehicle arrives.

The system spans three repositories:

- **`rampme-software`** (https://github.com/rangelovkiril/rampme-software) holds the backend (Bun + Elysia) and the frontend (Next.js). The backend runs in the cluster declared here. The frontend does not; it is a static site on Cloudflare Pages, so the cluster only ever serves the API at `api.rampme.site`.
- **`fleet`** (this repository) declares everything that runs on a single-node k3s cluster on a Hetzner VPS. Flux reconciles the live cluster state to match what is committed here.
- **`rampme-hardware`** (https://github.com/rangelovkiril/rampme-hardware) is the Raspberry Pi ramp firmware. It talks to the backend only through the ramp MQTT protocol, not through anything in this repository.

> [!NOTE]
> This README is oriented at a human landing on the repository for the first time. For the canonical contributor and agent rules, see `AGENTS.md`. For the full infrastructure runbook, see the [fleet wiki](https://github.com/rangelovkiril/fleet/wiki), which is the authoritative documentation for this cluster.

## Directory layout

```
clusters/hetzner/            the path Flux reconciles from
  flux-system/                Flux's own components, generated by flux bootstrap, DO NOT EDIT
  infra-controllers.yaml      Kustomization -> ./infrastructure/controllers
  infra-configs.yaml          Kustomization -> ./infrastructure/configs
  apps.yaml                   Kustomization -> ./apps
infrastructure/
  controllers/                envoy-gateway (HelmRelease), cloudflared
  configs/envoy-gateway/      Gateway, GatewayClass, EnvoyProxy
apps/
  rampme/                     namespace, backend/, imageupdateautomation.yaml
  lms/                        empty placeholder for a possible second, unrelated project
tofu/                         OpenTofu configuration for the Cloudflare account
.sops.yaml                    SOPS encryption rule
.mcp.json                     Cloudflare MCP server declarations
.gitignore                    OpenTofu working directories and transient output
LICENSE
```

`clusters/hetzner` is the entry point: it is the path given to `flux bootstrap`, and everything else is reached from there through Kustomizations. `infrastructure/` holds cluster-wide plumbing that applications depend on but that is not itself an application: the ingress controller and the tunnel daemon. `apps/` holds the actual workloads.

`tofu/` is outside the Flux reconcile paths entirely and is never applied by the cluster. It declares the Cloudflare side of the request path, the tunnel and its ingress mapping, DNS, and the Pages project, so that state stops living only in the Cloudflare dashboard. It is applied by hand; see `tofu/README.md`.

## Reconcile chain

Flux reconciles from `clusters/hetzner`. The `flux-system` Kustomization there brings up the rest in order, each stage declaring `dependsOn` the previous one, with `wait: true` and `timeout: 5m`:

```
flux-system            (clusters/hetzner)
  -> infra-controllers (Envoy Gateway HelmRelease, cloudflared)
  -> infra-configs     (Gateway, GatewayClass, EnvoyProxy)
  -> apps              (rampme namespace, backend, image automation)
```

`infra-controllers` and `apps` carry `decryption.provider: sops` with `secretRef.name: sops-age`, because both contain SOPS-encrypted secrets. `infra-configs` does not need decryption, since it has no secrets.

## How a change reaches the cluster

> [!IMPORTANT]
> A new Git revision triggers the dependent Kustomizations as soon as the source updates, it does not wait for the next interval. The intervals below are the drift-correction floor, not the deploy latency.

The `flux-system` GitRepository polls `main` every `1m0s`. Every Kustomization has `interval: 10m`, meaning that even with no new commit, Flux re-applies and corrects drift at least that often. The envoy-gateway HelmRelease and HelmRepository use `interval: 1h`. The image automation objects (ImageRepository, ImagePolicy) use `interval: 5m`, and ImageUpdateAutomation also uses `5m`.

In practice: a commit pushed to `main` is picked up by the GitRepository within a minute, and the affected Kustomization reconciles immediately after, not after a full 10 minute wait. New backend images are a separate loop: the application's CI publishes `prod-<timestamp>` tags to `ghcr.io`, the `rampme-backend` ImagePolicy picks the numerically highest tag matching `^prod-(?P<ts>[0-9]+)$`, and the ImageUpdateAutomation commits the new tag into `apps/rampme/backend/deployment.yaml` on `main`, which then flows through the same Kustomization chain.

> [!WARNING]
> Never hand-edit the image tag in `apps/rampme/backend/deployment.yaml`. The `# {"$imagepolicy": "rampme:rampme-backend"}` marker on that line is managed by Flux; a manual edit will be overwritten or will conflict with the next automated commit.

## Validating manifests locally

Each buildable path can be rendered with `kustomize` through `kubectl`:

```
kubectl kustomize clusters/hetzner/flux-system
kubectl kustomize infrastructure/controllers
kubectl kustomize infrastructure/configs
kubectl kustomize apps
```

> [!NOTE]
> `kubectl kustomize clusters/hetzner` itself fails, deliberately. That directory has no `kustomization.yaml`; Flux generates one for it automatically at bootstrap time. This is not a bug, do not add a `kustomization.yaml` there to make the command pass.

There is no CI in this repository yet, so running these commands locally before pushing is the only validation gate that exists.

## Editing an encrypted secret

Secrets are encrypted with SOPS for the age recipient declared in `.sops.yaml` (`encrypted_regex: ^(data|stringData)$`, applied to any `.yaml` file). The matching private key lives only on the maintainer's machine, with no backup elsewhere (tracked as issue #2).

To edit an already-encrypted secret in place, with the private key available to `sops`:

```
sops apps/rampme/backend/secret.yaml
```

This decrypts into an editor, and re-encrypts `data`/`stringData` on save. To encrypt a freshly written plaintext secret before the first commit:

```
sops -e -i apps/rampme/backend/secret.yaml
```

To inspect decrypted content without editing:

```
sops -d apps/rampme/backend/secret.yaml
```

> [!CAUTION]
> `apps/rampme/backend/secret.yaml` currently ships `REPLACE_ME` placeholders in plaintext `stringData`, not encrypted. Real MQTT credentials must be filled in and encrypted with `sops -e -i` before that file is ever committed with real values. Check every diff touching that file for plaintext secret material before committing.
